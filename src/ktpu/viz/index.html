KohakuTPU — live simulator

One elaborated xsim snapshot stays warm; each shape is a fresh operand image and control program replayed through it. Software never sees MXFP7 — operands go out as FP16 and MAG quantises them in hardware. Every number below is read out of the run that produced it; anything recorded earlier is labelled as recorded.

The machine, in five ideas

1

A cluster is the unit

One manager, a chain of 4 tensor CUs, one accumulator. 512 MAC/cycle each — 4×8×4 per CU, one 4×4 sub-tile against 32 K per cycle.

2

Numbers are MXFP7

int7 elements sharing an E5M3 block scale. Software never sees it: the host uploads FP16 and the hardware quantises, either on upload or on every read.

3

A mesh, not a bus

Clusters sit on routers. Memory hangs off the west edge with one port per mesh row, so a row's traffic never leaves it. This is the idea that makes it scale.

4

K is the outer loop

An output address recurs every Gm×Gn cycles, not every cycle. That is what lets the accumulator be one plain memory with a pipelined adder instead of rotating banks.

5

Three phases, overlapped

fill operands into L1, gemm the array, drain the finished tile. How well they overlap is the performance — see the working-pipeline view.

Why one port per row matters. With a single shared memory port, operand fetch cost 7.6 → 25.6 → 93.3 cycles per entry as clusters went 2 → 4 → 8, with nothing saturated. It was one server, not one wire. Splitting the port per row is what removed that.

…
Ready. The first run elaborates the design (~15 s); every run after is ~1 s.

The panel above is the plan, not a guess. It comes from the same tiling, padding and layout functions the run itself uses, so it cannot describe a different machine from the one that would execute — and it costs no simulator. Watch it when you change NCL: the cluster count divides N, so a shape that fits at two clusters can pad hard or overflow the bench RAM at eight.

Cluster count is compiled in. NCL sizes the mesh, the cluster array and the number of MAG memory ports, so it is part of the snapshot's identity — changing it re-elaborates and costs ~15 s instead of ~1 s. Every other control here is data the bench re-reads at time 0.

Operand distribution is not cosmetic. Under normal every output is a fully cancelled sum, so relative error is pinned at the operand's own precision however large K gets — the worst case that exists. Real weights and activations are correlated, which is what lowrank reproduces.

Where quantisation is paid changes the rate and must not change the answer. Software never builds int7 either way: the host uploads FP16 and the hardware converts, on the way in or on every read. On the way in it is paid once per tensor and the operand is half the bytes forever; on every read it is paid once per pass. Flip it and watch the error columns stay put — if they move, the fast path is a different circuit, not a faster one.

Cycles are the measurement; seconds and GFLOP/s are a clock assumption. The RTL produces cycles. mx_cluster_cu closed out-of-context at 325.6 MHz — unplaced, so an upper bound — with +0.155 ns of slack at 310 MHz, which is why the 300 MHz target is now a statement rather than a hope. The selector rescales every derived rate; no cycle count moves.

Verdict

—

Scored by sim._verdict, the same function run_matmul.py exits on — one definition, so the page and the command line cannot disagree about a run. The circuit is judged against the MXFP7 model, not against FP64: judging it against FP64 measures the format and the hardware together and calls the sum a tolerance, which is how a real defect hides inside an expected quantisation loss.

Workflow

How the clusters cooperate

Per cluster

clusteractive fromtospan fillgemmdrainidle

They share one image of everything. A, B and C are each a single region addressed by tile index, and a cluster is told which output tile to compute rather than which slice of memory it owns — which is the only arrangement in which any cluster can be handed any tile. When the grid gives each of them whole column bands they are asking for byte-identical A entries at the same moment; when there are fewer bands than clusters they are working down one band together and it is B that coincides. Either way one operand is shared and a shared fetch would divide it (the mechanism exists — peers on the FILL, leader election in the CU, a multi-destination emitter in MAG — and the driver does not arm it, because a follower cannot yet tell which fill an arriving entry belongs to).
One memory port per mesh row. A port serves the clusters in its own row and their traffic never leaves it. Routing is X then Y on coordinates clamped into the grid, so a flit addressed to (0,y) walks west to router (1,y) and only then takes the outward hop — which is why rows below the first need no west neighbour of their own, and why the agent can sit off the east edge at (NCOL+1,1).

Output tiling

Every cell is one pass — one kick of one cluster, which fills L1, sweeps K into the resident tile and drains it once. Colour is the cluster that owns it; the number is the order it is issued in. Click a tile to see the instructions that compute it; hovering an instruction below lights its tile back up. The grid is the unit of dispatch: all m_tiles × n_tiles of these cells are dealt across the clusters, so a problem with a narrow N is still wide work. They are dealt column band outermost and in contiguous runs, so every m-tile that reads one band of B stays with it while it is resident in L1 — with m outermost, B for the next band would evict it before the m loop came back.

Kernel program

The program as the CU will execute it: every flit decoded from the bits that were built, not read back off the planner. eoff is where a FILL lands in L1; aoff/boff are where the sweep reads. A FILL never lands in the range of the sweep already running — consecutive K chunks alternate banks. That is the banking, and nothing in the hardware interlocks it: a fill inside a live sweep corrupts a few sub-tiles and reports nothing. acc chains a sweep into the resident tile so K can exceed L1 without a partial round-tripping through memory. emit hands each sub-tile out as its last K block finishes it, which is what lets fuse turn the DRAIN behind it into a barrier instead of a second pass through the pipeline.
A pass marked prefetch is not this tile's work: the next pass's first FILL and sweep are moved in FRONT of this pass's barrier, so they overlap the write-back instead of waiting behind it.

L1 and residency 

      

      
A is double-buffered; B stays put. A GEMM retires
      when its sweep STARTS, so the CU runs the next FILL while the array is
      still reading — which only helps if the fill lands where the sweep is not
      looking, so consecutive K chunks alternate between two banks. Two is
      exactly enough: a sweep waits for the one before it, so only two chunks
      are ever live. Without it the array idled through every fill, 22.3% of the
      machine.
      
B does not change across the m loop. When every K chunk of one column
      band fits in the B side at once it is filled once per band and left
      there; re-filling it per m-tile was a quarter of all memory traffic. The
      counts below are read off the program, so residency is measured
      rather than assumed.

Resource utilisation 

      

      
Do not add these together. Every link counted here
      is full duplex: AR/R and AW/W are separate AXI channels — the RAM model
      drives reads and writes from two independent blocks and serves both in the
      same cycle — and the NoC's two directions are separate wires. Summing them
      prices capacity that never competes, and doing so once produced a reading
      of "91.5% of data movement" that closed off a whole line of optimisation
      which then turned out to be worth 14% of peak. What binds is the
      largest bar, never the total, and it is named above.
      
The memory and NoC counters are sums over MAG's memory ports, so each
      is divided by the port count to become a fraction of that port's own
      capacity.

    


    

      
Where the cycles go 

      

      


      
Operand fetch 

      

      
Fill time has two causes that look identical in a total:
      moving too many bytes, or moving them one exposed round trip at a time.
      Cycles per entry near the floor is bandwidth-bound — only reuse or
      a wider memory helps. Near the first-request latency it is serialised,
      and the fix belongs in the CU. The per-entry figure divides fill occupancy
      (summed over every cluster) by L1 writes on cluster 0 times the cluster
      count, because that is the only pair of counters the bench provides.

Why state plus the reason it could not advance

      

      
Each bar is a fraction of the resource it was counted
      on, and the basis is named. The MAG and fabric counters are summed
      over memory ports, so they are out of run × ports; the two marked
      cluster 0 are tapped on one CU and say nothing about the others.
      These buckets deliberately overlap — MAG's read engine runs
      concurrently with its write and host paths — so they are not a partition
      of the time and must not be summed into a "busy" figure.
      
Occupancy is summed over the CUs, so the cycle counts beside
      the bars total about NCL × elapsed when every cluster is busy; the
      percentage is out of run × NCL, which is what makes it a fraction.
      fill is operands moving into L1, gemm is the array
      multiplying, drain is the output tile leaving the accumulator. A
      fill-dominated profile is not a scheduling mistake: a pass moves
      (gm+gn)*nk L1 entries to do gm*gn*nk tile-ops, so
      arithmetic intensity is set by the L1 and accumulator sizes. Read
      bandwidth is demand — the bench RAM answers immediately, so real
      memory would push fill higher.

    


    

      
Memory image

      

      

      
Three regions at any cluster count: A, B and C are each
      one image addressed by tile, which is what lets an output tile go
      to whichever cluster is free. B and C used to be cut per cluster, back
      when a cluster owned a column band. Overlapping two of these is silent, so
      seeing the layout is the cheap way to notice. A pre-quantised operand
      occupies half the words.

Precision 

      

      
The count is the signal; the worst element is not.
      A handful of outputs cancel toward zero — four K blocks with independent
      scales, and an output small against its own partial sums has a large
      relative error by arithmetic rather than by fault. That moves
      max with the shape and the seed. What a real defect moves is
      how many elements are bad: a lost or mis-slotted sub-tile corrupts
      sixteen contiguous outputs at once and shifts p50 with them. Watch the
      rate, not the maximum.
