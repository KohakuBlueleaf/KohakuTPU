# DBG: the debug firmware interface

What the node firmware reports to the host, how the host reads it, and the
debug firmware the stack's tier-1 card tests need (tier 1: tiny kernels batched into one card session with a debug
firmware, each result checked against numpy on the host). Clause format,
ids and evidence tags follow `docs/spec/stack/README.md`.

Section 1 is what exists. Section 2 is what the debug firmware adds; every
clause there is `unproven` except DBG.CHK.001, the Verilated-card suite that
exists. Design choices with no spec answer are listed
under **Conflicts for ruling**, not decided here.

Paths are repo-relative. `fw/` is `software/firmware/`, `drv/` is
`software/driver/`, `rt/` is `software/application/kohakutpu/application/runtime/`.
`LOG` is the v9t6 card run `lenet_n1_nojit.log` (node 0, 2026-10-21, no JIT):

`CARD1` is the v9t6 card run of the debug firmware's tier-1 vectors (node 0
over XDMA at the idle profile, sys 100 MHz, 2026-10-22): the 11 clauses tagged
`silicon` in section 2 pass and each vector's mutant breaks it (Linux host

## 1. What exists

### 1.1 The completion report

- **DBG.RPT.001** `silicon` Every `RUN` submission ends in exactly one 32-byte completion entry: word 0 the tag, word 1 `[15:0]` status, `[31:16]` detail, `[63:32]` step index, word 2 node cycles from the start of the run (before the header read) to the result, the quiesce after a failure included, word 3 on success the firmware's count of words it dispatched itself (0 for a package lowered to `ENGINE` steps, L0.NQ.025) or the failure's value otherwise. The firmware stores the entry, then the CQ tail. (code: fw/kohakuaccel/queue/service.c:87-101, 239-242; drv/kohakuaccel/driver/node/queue/client.py:309-321; doc: docs/spec/node-queue.md:134-145; evidence: LOG:84, tag 0x83b, status, step and cycles decoded from this entry)
- **DBG.RPT.002** `silicon` In dispatch-engine mode a package whose engine issue count does not move for one wait bound fails `TIMEOUT` (0x30) with detail 11 (`ENGINE`, RUL.032) and value the engine's `STAT` word (magic 0xDE01 in `[63:48]`). (code: fw/kohakuaccel/package/interp.c:661-680; evidence: LOG:90, `status 30 detail 2 ... value de01064302350040`)
- **DBG.RPT.003** `unproven` The other status codes and their detail and value words: `UNIT_FAULT` 0x20 (detail the package unit index, or 0xffff for a coordinate not in the package; value the completion word), `MOVER_FAULT` 0x22 (detail the mover's fault code, value `MVSTAT`), `NO_REACH` 0x23 (detail the register), `BAD_STEP` 0x14 with detail 0xde (engine queue overflow, value `STAT`), the header and heap codes 0x10..0x18, 0x40, 0x50..0x54. 22 codes in all. (code: fw/kohakuaccel/include/ka/package/status.h:6-29; fw/kohakuaccel/dispatch/engine.c:88-110; interp.c:558-559, 625-627, 666-671; doc: docs/spec/node-queue.md:147-172)
- **DBG.RPT.004** `unproven` The first failure of a package is the one reported: a later failure in the same run changes neither status, detail nor value. (code: fw/kohakuaccel/dispatch/engine.c:12-20)
- **DBG.RPT.005** `silicon` On a failure the firmware prints one `PKGF u<i> (<x>,<y>) sent <n> recv <n> want <n> inflight <n>` line per package unit and one `PKGF stray <n> outstanding <n>` line, then quiesces: it drains completions while any are outstanding, for at most one wait bound, and empties the mailbox's completion queue. The reported step is the step the interpreter was on. (code: fw/kohakuaccel/package/interp.c:1565-1579; fw/kohakuaccel/dispatch/engine.c:315-331; evidence: LOG:84-89: step 0, the `PKGF` lines, and a `barrier` phase of 2,025,680 cycles, one bound)
- **DBG.RPT.006** `silicon` With the boot block's `TIMING` flag the firmware prints, after every `RUN`, one line `PKGT head <c> copy <c> bind <c> steps <c> barrier <c> local <0|1> total <bytes> first <c> last <c> sent <n>`: the phase cycles (`barrier` runs from the end of the steps to the result, a failure's quiesce included), whether the package was copied local, its size, the first and last send relative to bind, and the words the firmware sent itself (0 for a package lowered to `ENGINE` steps). (code: fw/kohakuaccel/package/interp.c:1582-1589; fw/kohakuaccel/include/ka/boot/args.h:15-16; evidence: LOG:89)
- **DBG.RPT.007** `silicon` After posting a failed completion the queue service prints `[ka] package <tag hex> failed: status <hex> detail <hex> step <dec> value <hex>`. (code: fw/kohakuaccel/queue/service.c:246-249; evidence: LOG:90)
- **DBG.RPT.008** `silicon` Order: the `PKGF` and `PKGT` lines are flushed to the ring before the completion is posted; the `[ka] package ... failed` line is printed after it. (code: fw/kohakuaccel/queue/service.c:239-249; evidence: the failure path ran at LOG:84-90 (service.c unchanged since af7c1bb), its lines in that order)
- **DBG.RPT.012** `unproven` A host that reads stdout once, right after the completion, can miss the `[ka] package ... failed` line until its next read. (code: fw/kohakuaccel/queue/service.c:239-249; drv/kohakuaccel/driver/node/queue/client.py:340-341; evidence: at LOG:84-90 the host's read caught the line)
- **DBG.RPT.009** `unproven` A `SIGNAL` step posts a `PROGRESS` (0x01) completion carrying the step index, the cycle counter, the step's 32-bit value truncated to 16 bits as detail, and its 64-bit value; the package keeps running. The host keeps these in `NodeQueue.progress`. (code: fw/kohakuaccel/queue/service.c:105-110; drv/kohakuaccel/driver/node/queue/client.py:318-321; doc: docs/spec/node-queue.md:141, 152)
- **DBG.RPT.010** `unproven` Per-step trace: with the boot block's `STEPS` flag the firmware prints `PKGS <first> <last> <cycle>` as each step (or round-robin dispatch group `first..last`) ends, the cycle counted from bind with the trace's own printing subtracted. One line costs about 4,000 node cycles (measured on the Verilated `card_v9_1n`, no named test). (code: fw/kohakuaccel/package/interp.c:1532-1553; doc: docs/spec/node-queue.md:63; the `KA_BOOT_F_STEPS` flag is bit value 8)
- **DBG.RPT.011** `unproven` In dispatch-engine mode the firmware queues steps ahead of the engine's issue, so a `PKGS` cycle is when the step was queued, and a failure's step index is the step being queued when the failure was seen, not the step the engine was issuing. (code: fw/kohakuaccel/package/interp.c:641-645, 1542-1543, 1574)

### 1.2 Fault printers per unit class

- **DBG.FLT.001** `unproven` A unit class's `describe(code, arg)` runs on a completion its classifier calls a fault, before the failure is recorded, and prints into stdout. The generic class has no printer. (code: fw/kohakuaccel/dispatch/engine.c:96-110; fw/kohakuaccel/include/ka/unit/unit.h:15-24; fw/kohakuaccel/unit/registry.c:20-26; doc: docs/arch/cpu/rv64-sys/firmware.md:252-274)
- **DBG.FLT.002** `unproven` `MG` (0x4D47) prints `[MG] fault, signal <code> arg <hex>`. `VC` (0x5643) prints `[VC] fault code <n> (<name>), signal <code>`, the name from `arg[7:0]`: 1 `F_DTYPE`, 2 `F_VSRC`, 3 `F_CHAIN`, 4 `F_OPCODE`, 5 `F_LEN`, 6 `F_LOOP`, 7 `F_VL`, 8 `F_REDVL`, 9 `F_CUDATA`. (code: fw/kohakutpu/units/matmul.c:6-17; fw/kohakutpu/units/vector.c:6-24)
- **DBG.FLT.003** `unproven` `SR` has no firmware class: an SR unit runs under the generic classifier and its fault fails `UNIT_FAULT` with no printed decode. The driver registers SR with a `CU_DBG` decoder. (code: fw/build.py:60-69; fw/kohakuaccel/unit/registry.c:28-36; drv/kohakutpu/driver/units/__init__.py:13, 47-65)
- **DBG.FLT.004** `unproven` A mover fault (`MVSTAT[31:28]` nonzero, `mover.fault_bits` [4]) fails `MOVER_FAULT`, read on every mover wait and every engine-mode watch. The host names codes 0..10 (none, index length, range, AXI, mode, element width, alignment, bound axis on XFORM, transform slot, configuration-queue overflow, bad fp32 index). (code: fw/kohakuaccel/package/interp.c:552-575, 661-669; drv/kohakuaccel/driver/device/mover.py:73-87; drv/kohakuaccel/driver/node/queue/client.py:57-58)

### 1.3 Timeouts

- **DBG.TMO.001** `silicon` With the submission's word 5 zero, each wait of a package is bounded in node cycles by the boot block's `timeout`. (code: fw/kohakuaccel/package/interp.c:1490; fw/kohakuaccel/queue/service.c:233; doc: docs/spec/node-queue.md:61, 121; evidence: LOG:84, 89, 90, every card `RUN` carrying word 5 zero)
- **DBG.TMO.007** `unproven` A nonzero word 5 replaces the boot block's `timeout` for that submission. (code: fw/kohakuaccel/package/interp.c:1490; fw/kohakuaccel/queue/service.c:233; doc: docs/spec/node-queue.md:121; evidence: no stack path submits a nonzero word 5)
- **DBG.TMO.002** `unproven` A `TIMEOUT`'s detail names the wait: 1 credit, 2 await (and engine-mode no progress), 3 barrier, 4 mover, 5 bell, 6 mailbox offer, 7 slot, 8 RX, 9 ack, 10 ring. (code: fw/kohakuaccel/include/ka/package/status.h:32-43; fw/kohakuaccel/dispatch/engine.c:200, 228, 258, 293, 312; fw/kohakuaccel/package/interp.c:969, 1004, 1026, 1206, 1254, 1272)
- **DBG.TMO.003** `silicon` Engine-mode waits are bounded on progress: the package fails only once the engine's issue count has stayed unchanged for one bound. (code: fw/kohakuaccel/package/interp.c:673-680; evidence: LOG:89: the `ENGINE` step 0 ran 10,741,399 cycles (`steps`) under a bound of about 2,000,000 before it failed)
- **DBG.TMO.008** `unproven` Mover waits are bounded on progress (no move finished for one bound); every other wait is bounded from its start. (code: fw/kohakuaccel/package/interp.c:547-575; fw/kohakuaccel/dispatch/engine.c:158-180; evidence: every card package ran in engine mode, and no logged failure is a firmware-path wait)
- **DBG.TMO.004** `silicon` The card ran with a boot bound of 2,000,000 cycles, the host's default then; the host now has no default (RUL.033) and its vector gives 2,000,000 explicitly (F-030). (code: drv/kohakuaccel/driver/node/boot/args.py; evidence: LOG:89: the failed package's quiesce, which runs out one bound, took 2,025,680 cycles (`barrier`))
- **DBG.TMO.009** `unproven` Every firmware time bound is in sysnode cycles (`rdcycle`); the firmware converts nothing by clock profile. The card runtime replaces the boot default with `timeout_seconds x the profile's sys clock` when it knows the profile. (code: fw/kohakuaccel/include/ka/hal/cpu.h:7-12; rt/card.py:222-225, 554; evidence: no recorded card log shows a scaled bound)
- **DBG.TMO.010** `silicon` A bound fires at the first check after more than `timeout` cycles without progress, so the failure lands up to one poll past the bound; it is never early. A `TIMEOUT` completion's `cycles` is the whole run from its start (head, copy, bind, the steps, then the failure's quiesce and report, interp.c:1487,1616), never the waited time, so it exceeds the bound by a fixed overhead that does not grow with the bound. (code: fw/kohakuaccel/package/interp.c:673-684, 1487-1616; fw/kohakuaccel/dispatch/engine.c:325-341; evidence: the Verilated card (v3 images, the engine-mode await package at bounds 100,000 / 200,000 / 400,000): `steps` = bound + 155 / 167 / 111 cycles; head + copy + bind about 1,060; after the failure (`barrier`, quiesce plus the `PKGF` prints) 13,796 / 13,760 / 13,764 in the production image, whose completions read 115,009 / 214,993 / 414,927; the debug image, which writes binary records instead of printing, read 202,529 at 200,000; vector DBG.TMO.010.late, on the Verilated card and on the card (`CARD1`))
- **DBG.TMO.005** `unproven` A full CQ holds the queue service with no bound (it yields until the host advances the CQ head). (code: fw/kohakuaccel/queue/service.c:90-92)
- **DBG.TMO.006** `unproven` The host's `NodeQueue.wait` raises `TimeoutError` with the firmware line after its own `timeout` seconds (default 300). Before each idle between polls it reads the firmware line and raises `FirmwareFatal` (state, fatal code, stdout) on a `FATAL` state; `wait_ready` raises on it too. (code: drv/kohakuaccel/driver/node/queue/client.py:179-192, 326-342)

### 1.4 stdout, stdin and the console tap

- **DBG.OUT.001** `silicon` Once the queue service has started, everything `ka_printf` prints goes through a 64-byte line buffer (flushed at a newline or 64 bytes) into the queue region's stdout ring. The host drains it on every poll and on `read_stdout`. The host's default ring is 4096 bytes. (code: fw/kohakuaccel/lib/stdio/stdio.c:7-31; fw/kohakuaccel/queue/service.c:43-70, 202; drv/kohakuaccel/driver/node/queue/client.py:86, 297-304, 428-454; doc: docs/spec/node-queue.md:174-182; evidence: LOG:85-90)
- **DBG.OUT.002** `unproven` A full stdout ring holds the firmware for one boot `timeout`, then drops the bytes and counts them in the line's second word (`SO_WR + 8`). The host reads only the produced count; nothing reads the lost count. (code: fw/kohakuaccel/queue/service.c:43-70; drv/kohakuaccel/driver/node/queue/client.py:428-448; doc: docs/spec/node-queue.md:180-182)
- **DBG.OUT.003** `silicon` The queue service prints a ready banner after it sets the state to ready: `[ka] node <mesh> ready: queue <addr> sq <n> cq <n>, <n> units, sig <hex>, classes <names>; boot cycles: main at <c>, ready at <c>`. (code: fw/kohakuaccel/queue/service.c:184-195, 213-214; drv/kohakuaccel/driver/node/queue/client.py:184-186; evidence: printed at every card boot (service.c unchanged since af7c1bb) and read into the host's console by `wait_ready`; no recorded log holds it)
- **DBG.OUT.004** `RTL` The load window's console FIFO is drained one byte per read of `CONS` (`{valid[8], byte}`, a write pops). (code: src/kohakuaccel/sysnode/cpu/rv64_load_win.v:88-115; evidence: the `rv64_win_2p2` bench, sim/verilator/harness/rv64_win_main.cpp:62-70, 192-220, passes only on the expected console text)
- **DBG.OUT.008** `unproven` Before a sink exists (boot, or an image with no queue) each byte the firmware prints goes to `R_CONSOLE` (control region 0x08); the FIFO holds `node.console_fifo_bytes` [256]; the driver drains it (`rv64load`, `NodeBoot.console`). (code: fw/kohakuaccel/lib/stdio/stdio.c:21-26; drv/kohakuaccel/driver/device/rv64load.py:189-197; drv/kohakuaccel/driver/node/boot/loader.py:95-97; evidence: the bench runs a probe image, not the `ka` firmware, through its own C++ drain, and never fills the FIFO; the dispatcher prints nothing before its sink on a good boot)
- **DBG.OUT.005** `unproven` `ka_debug` writes the console tap directly. The fatal-trap path writes `[ka] fatal trap` to the tap and `[ka] fatal trap cause=<hex> epc=<hex> tval=<hex>` to the ring. (code: fw/kohakuaccel/lib/stdio/stdio.c:33-38; fw/kohakuaccel/hal/cpu/trap.c:20-27; doc: docs/arch/cpu/rv64-sys/firmware.md:159-168)
- **DBG.OUT.006** `unproven` Boot and queue-setup failures print to the console tap only: `[ka] no boot block`, `[ka] boot block version`, `[ka] <n> units, firmware holds 16`, `[ka] no queue at`, `[ka] bad queue geometry`. (code: fw/kohakuaccel/boot/args.c:10-28; fw/kohakuaccel/queue/service.c:112-129)
- **DBG.OUT.007** `unproven` stdin: the host writes whole lines of the stdin ring and then its written count; the firmware reads a byte at a time. (code: drv/kohakuaccel/driver/node/queue/client.py:456-469; fw/kohakuaccel/queue/service.c:72-85; doc: docs/spec/node-queue.md:192-194)

### 1.5 Exit words and the fatal state

- **DBG.EXIT.001** `RTL` A program ends by a store to `R_EXIT`; the host reads the word at `HR_EXIT` once `HR_STATUS[3]` (exited) or `[2]` (halted) is set. (code: fw/kohakuaccel/hal/cpu/trap.c:13-18; doc: docs/spec/control-registers.md:866-867, 912; evidence: the `rv64_win_2p2` bench, sim/verilator/harness/rv64_win_main.cpp:191-220, polls `STATUS & 0xc` and checks the exit word)
- **DBG.EXIT.005** `unproven` `NodeBoot.status` decodes `HR_STATUS` and reads the exit word and halt PC once the core has stopped. (code: drv/kohakuaccel/driver/node/boot/loader.py:86-93; evidence: the bench decodes in C++; no card or Verilated runtime path stops its firmware)
- **DBG.EXIT.002** `unproven` Exit words: `0xE0..` | `mcause` (trap), `0xE1..` | reason (boot block: 1 magic, 2 version, 3 units past `fw.max_units` [16]; 0x10 no queue or bad geometry), `0xE2..` | run count (task stack overrun), `0x5701..` | the host's 32-bit value (`STOP`). (code: fw/kohakuaccel/include/ka/hal/cpu.h:36-38; fw/kohakuaccel/include/ka/os/task.h:67; fw/kohakuaccel/apps/dispatcher/main.c:23-26; fw/kohakuaccel/queue/service.c:199-201, 268; fw/kohakuaccel/os/task/task.c:176-178)
- **DBG.EXIT.003** `unproven` Once the queue exists, a fatal stop flushes stdout and writes the firmware line's state `FATAL` (3) with the exit code. `wait_ready` and the daemon's `node_ready` raise with that line and the stdout text. (code: fw/kohakuaccel/queue/service.c:25-41; drv/kohakuaccel/driver/node/queue/client.py:153-158, 187-190; drv/kohakuaccel/driver/daemon/server.py:432-437; doc: docs/spec/node-queue.md:93)
- **DBG.EXIT.004** `unproven` On `STOP` the service prints `[ka] stop: <n> entries, task stack <n> B used, <n> switches, <n> idle passes`, posts the completion, sets `STOPPED` and exits `0x5701..` | value. (code: fw/kohakuaccel/queue/service.c:256-268)

### 1.7 Firmware images and build

- **DBG.BLD.001** `silicon` The card runs `build/fw/kohakutpu_node.elf`: the dispatcher (boot, os, queue, package, dispatch, unit, apps/dispatcher) with the `MG` and `VC` classes. (code: fw/build.py:57-69; rt/card.py:55, 198, 226; evidence: the card runtime loads it at every boot unless given another image (rt/card.py:198); LOG:1-5 is that runtime's session)
- **DBG.BLD.002** `unproven` The build defines `-DEXIT_ADDR=0x20000` for every image, `-DCPUPROBE_MESH=1` for `cpuprobe_m1` only, and `-DKA_DEBUG=1 -DKA_DEBUG_LAST=4` for `kohakutpu_debug` only (the debug image: `kohakutpu_node`'s sources, every one `-Os`). Sources compile `-O2`, with `-Os` for `package/`, `os/` and `queue/`; `--toolchain gcc|clang`. The other images are `kohakuaccel_node`, `memprobe`, `xfprobe`, `osprobe`, `cpuprobe`, `cpuprobe_m1`. (code: fw/build.py:28-45, 57-103, 114-121, 261-289)
- **DBG.BLD.003** `unproven` The build refuses an image whose `.text` exceeds `node.imem_bytes` [32768] or whose `.bootargs + .rodata + .data + .bss + .noinit + .stack` exceeds `node.spad_bytes` [32768] (`DOES NOT FIT`, exit 1). (code: fw/build.py:124-135, 280-289; fw/kohakuaccel/arch/rv64/node.ld)
- **DBG.BLD.004** `unproven` The current `kohakutpu_node` build uses 30,048 of 32,768 B of IMEM (`.text`); `kohakutpu_debug` uses 28,640 B and `kohakuaccel_node` 29,024 B of IMEM. (code: build/fw/kohakutpu_node.size:3-9; build/fw/kohakuaccel_node.size:3)

### 1.8 The host side

- **DBG.HOST.001** `silicon` `NodeQueue.wait` raises `NodeError(completion, read_stdout())` for a final completion whose status is not `OK`. Its message is `Completion.describe()`, then `node said:` and the stdout text. (code: drv/kohakuaccel/driver/node/queue/client.py:62-73, 326-342; evidence: LOG:84-90)
- **DBG.HOST.002** `silicon` `Completion.describe` names the status from `layout.STATUS` and a `TIMEOUT`'s detail from `layout.WAITS`. (code: drv/kohakuaccel/driver/node/queue/client.py:47-54, 59; drv/kohakuaccel/driver/node/queue/layout.py:47-83; evidence: LOG:84, `TIMEOUT waiting on await`)
- **DBG.HOST.009** `unproven` `Completion.describe` names a `UNIT_FAULT`'s unit and signal word, and a `MOVER_FAULT`'s code from `mover.FAULTS`. (code: drv/kohakuaccel/driver/node/queue/client.py:55-58; evidence: no logged unit or mover fault)
- **DBG.HOST.003** `unproven` `layout.WAITS` names details 1..6 only (5 as `doorbell`); details 7..10 print as bare numbers. `test_queue_layout_matches_the_firmware` checks `STATUS` against `status.h` and does not check `WAITS`. (code: drv/kohakuaccel/driver/node/queue/layout.py:75-83; drv/tests/test_node_queue.py:63-65)
- **DBG.HOST.004** `silicon` The card runtime parses each successful run's stdout `PKGT` line into `phases`. (code: rt/card.py:437-444; evidence: every logged card run printed a `PKGT` line (`TIMING` always set) and `_result` ran for each of the 2035 successful runs (LOG:5); card.py unchanged since af7c1bb)
- **DBG.HOST.010** `unproven` The card runtime parses `PKGS` lines into `steps` as `(first, last, cycle, "<op> u<unit> n<count>, ...")` from its own copy of the package. (code: rt/card.py:445-452; evidence: the logged runs did not set `STEPS`)
- **DBG.HOST.005** `silicon` One boot serves every package of a session: the runtime boots each node once, waits for ready, and submits packages until it stops. (code: rt/card.py:204-231, 368-399; evidence: LOG:5, 2035 kernel runs in one boot)
- **DBG.HOST.006** `unproven` With `KOHAKUTPU_KEEP_FAILED=<dir>` the runtime writes a failed package's bytes and bindings to `<dir>/failed_<run>.pkg` and `.json`. (code: rt/card.py:73, 356-365, 393-397)
- **DBG.HOST.007** `unproven` The driver decodes each unit kind's `CU_DBG` word: `MG` compute `[63:32]` and memory `[31:0]` cycles, cumulative; `VC` `[31:0]` of the last run; `SR` `[31:0]`, cumulative. (code: drv/kohakutpu/driver/units/__init__.py:20-65)
- **DBG.HOST.008** `unproven` With `faults=True` a multi-node run reports a node that faults or times out as `{"fault": text}` and still waits for the others; a node report the runtime cannot parse is `garbled node report`. (code: rt/card.py:400-421)

### 1.9 The card daemon

- **DBG.DMN.001** `unproven` The daemon serves `node_stdout`, `node_state`, `node_units`, `node_counters` and `node_heap_stats` as reads. Its waiting ops return the completion and, for a failed one, the stdout text; `node_ready` raises on a `FATAL` state. Its tests drive the Python spec double, not a Verilated node. (code: drv/kohakuaccel/driver/daemon/server.py:380-437; doc: docs/spec/node-queue.md:239-259; drv/tests/test_daemon_node.py)

## 2. The debug firmware the stack needs

A clause here is `unproven` unless its tag says otherwise. Where a clause depends on a design
choice, it names the open choice (O-n) under Conflicts for ruling.

### 2.1 Per-step trace

- **DBG.TRACE.001** `silicon` A traced package yields one record for each step it executes, in execution order: the step index (or `first..last` for a dispatch group), its opcode, its unit index, its end cycle counted from bind with the trace's own cost subtracted, and the counters O-1 chooses. The debug image writes a 64-byte `STEP` record per step of a run submitted with `RUN_F_TRACE` (or under the boot flag `STEPS`) into its debug region; the host decoder gives the unit index only for an op that names a unit, and the unit's firmware counters only on the firmware path. (code: fw/kohakuaccel/package/interp.c:1572-1581; fw/kohakuaccel/package/debug.c; rt/card.py; software/rust/crates/ktpu-debug/src/lib.rs; evidence: vector DBG.TRACE.001.memops on the Verilated card and on the card (`CARD1`))
- **DBG.TRACE.002** `unproven` Trace records reach the host whole, or the host reports the loss: a trace reader checks the ring's lost count (`SO_WR + 8`, DBG.OUT.002) or its O-8 equivalent, and a nonzero count fails the test.
- **DBG.TRACE.003** `silicon` Tracing does not change results: a package's output bytes are the same with tracing on and off. (evidence: vector DBG.TRACE.003.transpose on the Verilated card and on the card (`CARD1`))
- **DBG.TRACE.004** `silicon` A trace record says which clock its cycle is (firmware queue time or engine issue time, DBG.RPT.011); O-2. The `STEP` record's flag 1 marks a step queued to the dispatch engine (`clock: "engine"`); a run submitted with `RUN_F_NOENGINE` (debug image only) runs on the firmware path (`clock: "firmware"`). (code: fw/kohakuaccel/package/debug.c; fw/kohakuaccel/package/interp.c; evidence: vector DBG.TRACE.004.clock on the Verilated card and on the card (`CARD1`))

### 2.2 Buffer dumps

- **DBG.DUMP.001** `silicon` A dump request names buffers and a point: after step k, or at a failure. A dump returns each buffer's bytes keyed by its name. The host's table names them (`name -> (address, bytes)`): a package the card runtime sends is bound, so it carries no buffer entries (`build.packages`, L1.LOW.012). `NodeCard.run(dump=..., after=k)` runs each package cut after its step k (the unlowered step index, as a `NOENGINE` trace counts it) and puts the dump under `"dump"`, or on a failure as the `NodeError`'s `dump`. `tools.l1.run(dump=True)` dumps every parameter. (code: rt/card.py `cut`, `NodeCard.dump`, `NodeCard.run`; software/application/kohakutpu/application/tools/l1.py; evidence: vector DBG.DUMP.001.after_step on the Verilated card and on the card (`CARD1`))
- **DBG.DUMP.002** `unproven` A failure dump is taken after the quiesce of DBG.RPT.005 and records whether it drained (`outstanding == 0`). Bytes from a run that did not drain are marked unstable. The host reads only after the completion, which the firmware posts after the quiesce. `NodeCard.drained` takes the debug image's FAIL record flag, or else the production image's last `PKGF stray <n> outstanding <n>` line. A host `TimeoutError`, or a node not yet waited for in a multi-node run, also marks the bytes unstable. (code: rt/card.py `NodeCard.drained`, `NodeCard.run`; evidence: vector DBG.DUMP.002.drained, tier 0)
- **DBG.DUMP.003** `unproven` Any memory the debug firmware writes for a dump or a trace is a region the host assigned at boot through the boot block; the firmware allocates no DRAM. The debug image writes only its `DEBUG` region (L0.BOOT.026), and dumps are host reads (RUL.076). (code: fw/kohakuaccel/package/debug.c; doc: owner ruling: the firmware uses only the regions the host assigns at boot (queue, scratch, any OS heap) through the boot block and never allocates DRAM)
- **DBG.DUMP.004** `unproven` The dump mechanism is the host's (RUL.076): the host reads after the completion, and "after step k" is a package the host cuts at k. There is no firmware code for dumps. (code: rt/card.py `cut`)

### 2.3 The failing step's report

- **DBG.FAIL.001** `silicon` A failed package's report carries: the tag; the step index; the step's opcode; the unit's package index, coordinate and kind; the status, detail and value, each decoded by name; the unit class's fault decode; every unit's counters (today's `PKGF`); the mover status word; and the last completions per unit (count and storage O-4). The debug image writes one `UNIT` record per package unit and a `FAIL` record; the last `fw.debug.last` [4] completion words per unit are kept in the region on the firmware path. The card runtime reruns a failed package once traced and off the engine (RUL.075), where the unit counters are the firmware's. (code: fw/kohakuaccel/package/debug.c; fw/kohakuaccel/package/interp.c:1593-1610; fw/kohakuaccel/dispatch/engine.c; rt/card.py; evidence: vector DBG.FAIL.001.await on the Verilated card and on the card (`CARD1`))
- **DBG.FAIL.002** `silicon` The whole report is in the host's hands when the completion is: every report line or record is written before the completion is posted (unlike today's `[ka] package ... failed` line, DBG.RPT.008). The debug image writes its records, and prints its `[ka] package ... failed` line, before `ka_flush` and the CQ post. (code: fw/kohakuaccel/queue/service.c:244-256; evidence: vector DBG.FAIL.002.at_completion on the Verilated card and on the card (`CARD1`))
- **DBG.FAIL.003** `unproven` The host names every status and detail code the firmware can raise. Its tables are generated from, or checked against, the firmware's headers and the RTL fault encodings; they are never hand copies. (Conflict C-1.)
- **DBG.FAIL.004** `unproven` Every unit kind in the machine schema has a fault decode, in the firmware or on the host (O-5; Conflict C-2).
- **DBG.FAIL.005** `silicon` In dispatch-engine mode the report names both the step the firmware was queuing and the engine's issue count when the failure was seen (O-2). The debug image reads the engine's `STAT` issue count (`[31:16]`) when a run's first failure is recorded (`ka_engine_fail`). It writes the count as the `FAIL` record's word 7 when the record's engine flag is set. The decoder gives it as `issued` beside `step`; for a firmware-path failure `issued` is null. (code: fw/kohakuaccel/dispatch/engine.c; fw/kohakuaccel/package/debug.c; software/rust/crates/ktpu-debug/src/lib.rs; evidence: vector DBG.FAIL.005.engine_issue on the Verilated card and on the card (`CARD1`))

- **DBG.FAIL.006** `RTL` On every package failure, production and debug firmware retain the first failure's engine/mover snapshot before `de_end()` clears or rebases the engine and before quiesce drains completions. Before posting the completion, both images print `PKGF de stat <hex> moves <hex> mvstat <hex> xfdata <hex>` and `PKGF de ctr <hex> ...` (counter index order). The snapshot is reset per package and is not replaced by secondary faults during quiesce. The reads are consecutive volatile loads, not a simultaneous hardware latch: hardware may progress between reads. No snapshot register is written, no queue is popped, and no transform selector is changed. The host exposes raw words and named fields as `NodeError.snapshot`; absent lines from older images give null, malformed lines give `snapshot_error` without masking the completion. `KOHAKUTPU_KEEP_FAILED` writes a JSON object with `bindings`, `node`, `completion`, `snapshot`, `snapshot_error`, and `console`, beside the bound `.pkg`, named `failed_<run>_n<node>_t<tag hex>`. These records retain the original run, not a debug rerun. Multi-node fault results also carry the snapshot. (code: fw/kohakuaccel/dispatch/engine.c `ka_engine_snapshot`, `ka_engine_fail`, `ka_engine_report`; fw/kohakuaccel/package/interp.c `ka_package_run`; drv/kohakuaccel/driver/node/queue/client.py `failure_snapshot`; rt/card.py `_keep_failed`, `_collect`)

#### Snapshot registers and read-only contract (DBG.FAIL.006)

Offsets below are **node processor control-region offsets**, not host MMIO addresses.

| Offset | Snapshot field | Decode and side-effect-free read evidence |
|---|---|---|
| `0x300` | `raw.stat`, `stat` | DE_STAT: magic `[63:48]`, log2 queue depth `[47:40]`, log2 counter count `[39:36]`, overflow `[35]`, clearing `[34]`, blocked head `[33]`, enabled `[32]`, issued entries `[31:16]`, queued entries including head `[15:0]`. `dispatch_engine.v:235-246` is a combinational read mux. |
| `0x308` | `raw.moves`, `moves.issued`, `moves.done` | MOVES: zero-extended issued GO count in high 32 bits, completions relative to last clear in low 32 bits; each count is modulo `CTR_W` (12 in this engine). Same combinational mux, no CTL write. |
| `0x380 + 8k` | `counters[k]` | All exposed unit completion counters, up to the engine's 16-register window, read in index order. Same mux; the RAM write enable is `clearing || inc_v` (`dispatch_engine.v:145-152`), independent of read address. Zero counters are meaningful; they are not omitted. No-engine nodes produce no counter values. |
| `0x20` | `raw.mvstat`, `mover` | MVSTAT: ROOM `[33]`, busy `[32]`, fault code `[31:28]` and its `mover.FAULTS` name, free-running completed moves `[27:0]`. `rv64_syscore.v:774-799` registers the mover output wires in the return mux; it sends no read strobe to the mover. |
| `0x1d8` | `raw.xfdata` | The transform bank's **currently selected** readback, retained raw because the selector is not readable. With selected word 0 this is bank fault; word 1 is selected occupant geometry. `xform_bank.v:160-169` is a combinational mux; clearing the fault requires `cfg_en` (`:145-154`), which reads do not assert. This is not a busy/grant observation. |

For every row, `rv64_syscore.v:632-660` gates queueing, configuration and shared-window arbitration on `ctrl_wr = mem_started && sel_ctrl && m_st_q`. Reads therefore neither clear the engine nor hold its issue path through `cpu_sh`. Engine clear separately resets GO/issue counts and rebases mover completions (`dispatch_engine.v:220-230`), so taking this snapshot after clear is invalid. A node built without an engine returns zero (`rv64_syscore.v:835-840`); test magic before interpreting engine fields. MVSTAT's absolute completion count must not be compared directly to the rebased MOVES count. Issued GOs >= done moves is valid for the vectors' short, non-wrapping, settled move, not a general monotonic assertion across modulo wrap or sequential live reads.

The mover exposes only busy, fault, done and ROOM (`mm_mover.v:73-81`), not a CPU-readable register bus. Internal configuration occupancy, AXI outstanding counts, feeder/output FIFO counts, state machines, transform busy/grant/start/done and reservations have no additional CPU readback. They cannot be added to a firmware snapshot without an RTL interface change. Selecting a different transform register would require a write and is outside this read-only snapshot.

Vectors `DBG.FAIL.006.production_timeout` and `.debug_timeout` issue a full-line fill, wait for its completion, issue four harmless mailbox ARG writes, then wait for a unit completion never sent. They require a TIMEOUT, a live blocked engine, exact issue count, one issued and completed GO, all counters, consistent decoding and persisted JSON. The fault variants require MOVER_FAULT for an unsupported mover mode in each image. Mutant `dbg/snapshot_after_clear` boots separately built firmware that defers capture until the report after `de_end`; it must fail these checks rather than merely dropping a host field.

### 2.4 The batched session

- **DBG.SESS.001** `silicon` A tier-1 session boots the debug firmware once per node and runs many tiny packages, each with its own completion, trace, dumps and report. A failed package does not end the session: the firmware quiesces and serves the next entry, and the host records the failure and goes on (O-9). The host restarts the firmware only when a failure did not drain (RUL.082). (code: fw/kohakuaccel/queue/service.c:216-276; rt/card.py; evidence: vector DBG.SESS.001.goes_on on the Verilated card and on the card (`CARD1`))
- **DBG.SESS.002** `silicon` Every trace record, dump and report line can be traced to the submission it came from (O-6). Every debug record carries its submission's tag in word 1 (RUL.079). (code: fw/kohakuaccel/package/debug.c; fw/kohakuaccel/queue/service.c; evidence: vector DBG.SESS.002.tags on the Verilated card and on the card (`CARD1`))
- **DBG.SESS.003** `unproven` For every package, the firmware's wait bound expires before the host's wait. A hang therefore ends as a `TIMEOUT` completion with its report, never as a host `TimeoutError` (Conflict C-3). `DebugSession(card, seconds, wait)` boots the debug image with a boot-block bound of `wait` seconds at the card's sysnode clock (RUL.033). Each run's host wait is the budget left, and a run is refused when that does not exceed `wait`. The session restores the production image and its bound on exit. Host waits and the budget count the node's own time (`NodeQueue(clock=...)`): wall seconds on a card, modelled sysnode seconds on a Verilated card, so the ordering holds at any model speed; a wall-clock `alarm` there ends a wait as `OverBudget`, never as a `TimeoutError`. (code: rt/session.py, node/queue/client.py, rt/card.py `VerilatorCard`; evidence: software/application/tests/runtime/test_session.py, software/driver/tests/test_node_queue.py)
- **DBG.SESS.004** `unproven` While it polls, the host's wait checks the firmware line's state. A `FATAL` state ends the session at once with the fatal code, the stdout ring and the console tap's bytes (DBG.TMO.006). `DebugSession` turns the queue's `FirmwareFatal` into `SessionFatal` with each node's console tap, and leaves the stopped firmware in place. (code: drv/kohakuaccel/driver/node/queue/client.py `wait`; rt/session.py; evidence: drv/tests/test_node_queue.py::test_a_wait_ends_when_the_firmware_goes_fatal, test_session.py)
- **DBG.SESS.005** `silicon` One session completes in under 1 minute. `DebugSession(seconds=60)` is the budget. A run that the time left cannot hold raises `SessionBudget`; a failed run is recorded, and the session goes on. (code: rt/session.py; evidence: vector DBG.SESS.005.budget on the Verilated card and on the card (`CARD2` in [../isa/vector.md](../isa/vector.md)))

### 2.5 Selection and budget

- **DBG.SEL.001** `unproven` The debug firmware speaks the production ABIs (`KABOOT1` v3, `KAQUEUE1` v3, `KAPK` v2), so one driver runs both images; both carry the `.ka_abi` words the host checks (L0.BOOT.027). (code: fw/kohakuaccel/include/ka/boot/args.h:8-9; fw/kohakuaccel/include/ka/queue/layout.h:6-7; fw/kohakuaccel/include/ka/package/format.h:8-25)
- **DBG.SEL.002** `unproven` The debug firmware fits `node.imem_bytes` [32768] and `node.spad_bytes` [32768] by the build's fit check (DBG.BLD.003). The debug code is a separate image, `kohakutpu_debug` (RUL.073; 28,640 B IMEM; DBG.BLD.004), which the host selects per session: `NodeCard(debug=True)` or `NodeCard.load(debug=True)` boots it with a debug region (L0.BOOT.026). (code: fw/build.py; rt/card.py)
- **DBG.SEL.003** `silicon` The machine schema lists an image's debug features as firmware features (2p.3). The stack reads them from the schema and refuses a trace or dump request, by clause id, on an image that lacks them. The machine row `fw.debug` names the debug image, its features and its last-completion depth; the host reads an image's own features from its `.ka_abi` words and refuses a traced run, or a debug load, of an image without them with `DBG.SEL.003`. (code: scripts/py/machine/table.py; drv/kohakuaccel/driver/node/boot/abi.py; rt/card.py; doc: [../machine.md](../machine.md); evidence: vector DBG.SEL.003.refuse on the Verilated card and on the card (`CARD1`))

### 2.6 The host API

- **DBG.API.001** `unproven` One host decoder turns the firmware's output into typed results: per package, the completion, the trace records, the dumps as arrays keyed by binding name, and the failure report. Callers never parse firmware text. Where the decoder lives is O-7.
- **DBG.API.002** `unproven` A record the decoder cannot parse fails the test that produced it; it is never skipped. (code: rt/card.py:412-418)

### 2.7 Value checks

- **DBG.CHK.001** `RTL` On a Verilated card running `kohakutpu_node`, one boot per module runs many packages, and each result is checked on the host: against numpy computed from the same inputs, or against fixed values (`memops`, `fill`, `remote`). (code: software/application/tests/test_l1_examples.py:29-44, 52-418; rt/card.py:55, 461-479; evidence: software/application/tests/test_l1_examples.py, the module-scoped `card1` and `card2` fixtures and every test using them)
- **DBG.CHK.002** `unproven` Every tier-1 value test compares the card's result against numpy computed on the host from the same inputs, within the tolerance its NUM clause gives. No behaviour model is the oracle. The host reads results only after the package's completion. (doc: owner rule: no behaviour model as a test oracle, values come from the card with a debug firmware or a small Verilator model; docs/spec/node-queue.md:234-237)
