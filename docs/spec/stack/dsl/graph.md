# DSL: the `kt` tracer and the graph it produces

`kohakutpu.language.dsl` (`kt`) traces a Python function once per
specialisation into a tree of L2 statements and prints it as an L2 module.
The stack keeps the tracer in Python and hands the Rust backend the
traced graph (owner ruling: the DSL is a Python tracer producing a graph;
the Rust backend analyses it and produces L2 and the steps after; the
tensor-level API and the tinygrad device hand Rust their programs the same
way); the graph
contract below (DSL.GRAPH) is what the current tracer's output implies.
Clause format, ids and evidence tags: `../README.md`.

Evidence on this page:

- `silicon`: the construct's code is the same as in the tree of the
  2026-10-21 card run, `af7c1bb` (a clause's evidence says where it
  compared), and the generators of the
  455 card kernels at `af7c1bb` (`software/kohakutpu/application/kohakutpu/application/kernels/{vector,convert,matmul,transpose}.py`,
  every one built by `Kernel.build` with a `TensorSpec` for every port)
  used it, their L1 showing the
  instruction it lowers to. A refusal or error path is never `silicon`.
- `RTL`: a tinygrad run on the Verilated card whose generated kernels use the
  construct.
- `unproven`: neither. Every trace-time refusal is a host check no card run
  witnesses; each is listed so a test can name it.

Machine facts are machine-schema parameters with the v9t6 value in brackets.
The tracer reads `vc.lanes` and `vc.chunks` from its supplied machine (RUL.018),
and its target from `machine.target` (RUL.010):
`mg.count` [2], `vc.count` [2], `card.nodes` [4; the card run used 1],
`vc.lanes` [16, one 32-byte word of f16, the lanes of a chunk],
`die.word_bytes` [32], `vc.vlmax` [128]
(`boards/multimesh_v9t6.json:5`, `:74-95`). A GT4 register holds the
`vc.vlmax` values as a band of 4 rows by 32 columns (two `vc.lanes` chunks a
row).

## 14. The graph as JSON
